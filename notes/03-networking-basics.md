# Заметки под мой личный курс DevSecOps

## Тема 3. DNS и проверка HTTPS-соединения

**Статус:** начальная проверка DNS и HTTPS выполнена; далее изучаем HTTP-ответ.

### Цели

- Понять, как DNS связывает доменное имя с IP-адресом.
- Различать DNS-резолвер и авторитетный сервер.
- Проверять HTTPS-доступность и читать HTTP-статус.

## 1. DNS-запрос с VPN

Выполнена команда:

```bash
nslookup github.com
```

Наблюдение с включённым VPN:

```text
Server: 198.18.0.2
Address: 198.18.0.2#53

Non-authoritative answer:
Name: github.com
Address: 240.0.0.180
```

`Server` — DNS-сервер, которому отправлен запрос; `#53` означает порт DNS 53. Ответ `Non-authoritative` сам по себе не является ошибкой: ответ вернул резолвер, а не авторитетный сервер домена.

Диапазон `198.18.0.0/15` зарезервирован для тестирования сетевого оборудования, а `240.0.0.0/4` зарезервирован, а не предназначен для обычной публичной маршрутизации ([реестр специальных IPv4-адресов IANA](https://www.iana.org/assignments/iana-ipv4-special-registry)). По этому наблюдению можно предположить, что VPN использует DNS-посредник или синтетический ответ; конкретную конфигурацию VPN один запрос не раскрывает.

## 2. DNS-запрос без VPN

Повторный `nslookup github.com` без VPN показал:

```text
Server: 192.168.0.1
Address: 192.168.0.1#53

Non-authoritative answer:
Name: github.com
Address: 140.82.121.3
```

`192.168.0.1` — адрес из частного диапазона, часто используемый роутером или локальным DNS-посредником. `140.82.121.3` — публичный IPv4-адрес, полученный для имени в момент проверки. DNS-адреса могут меняться. GitHub публикует актуальные диапазоны своих IP через Meta API ([документация GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses)).

Разница между двумя ответами согласуется с тем, что VPN меняет путь DNS-запроса или способ отображения адресов. Это вывод по наблюдениям, а не установленная причина.

## 3. Проверка HTTPS через VPN

Выполнена команда:

```bash
curl -I --max-time 15 https://github.com
```

Важные части ответа:

```text
HTTP/2 200
server: github.com
strict-transport-security: max-age=31536000; includeSubdomains; preload
```

- `-I` запрашивает только HTTP-заголовки, без тела страницы.
- `--max-time 15` ограничивает время выполнения 15 секундами.
- `HTTP/2 200` означает, что HTTPS-запрос завершился успешно и сервер вернул статус `200`.
- `server: github.com` обозначает сервер в HTTP-ответе.
- `strict-transport-security` — заголовок HSTS, сообщающий браузерам использовать HTTPS для домена.

В полном ответе `curl` присутствовали также cookie-заголовки; они не нужны для конспекта и здесь не сохраняются.

## 4. Заголовки безопасности

Чтобы не печатать длинные cookie-заголовки, статус и выбранные заголовки отфильтровали:

```bash
curl -sSI --max-time 15 https://github.com | grep -Ei '^(HTTP/|server:|strict-transport-security:|content-security-policy:|x-frame-options:|x-content-type-options:)'
```

Ответ содержал `HTTP/2 200`, HSTS, `x-frame-options: deny`, `x-content-type-options: nosniff` и длинную Content Security Policy.

- HSTS: `max-age=31536000` задаёт срок действия в секундах (примерно один год); `includeSubdomains` распространяет политику на поддомены ([RFC 6797](https://www.rfc-editor.org/rfc/rfc6797)).
- `X-Frame-Options: deny` запрещает браузеру показывать страницу во фрейме/iframe, что помогает против clickjacking ([RFC 7034](https://www.rfc-editor.org/rfc/rfc7034/)).
- `X-Content-Type-Options: nosniff` запрещает браузеру угадывать тип содержимого вместо использования заявленного MIME-типа ([Fetch Standard](https://fetch.spec.whatwg.org/)).
- CSP начинается с `default-src 'none'`, задавая запрет по умолчанию для ресурсов, для которых не заданы более конкретные правила. Дальше сервер перечисляет разрешённые источники для отдельных типов ресурсов. `frame-ancestors 'none'` запрещает встраивать страницу в другие страницы ([CSP Level 3](https://www.w3.org/TR/CSP/)).

## 5. Перенаправление HTTP на HTTPS

Проверили ответ на незашифрованный HTTP-запрос:

```bash
curl -sSI --max-time 15 http://github.com | grep -Ei '^(HTTP/|location:)'
```

Ответ:

```text
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
```

`301 Moved Permanently` сообщает, что предпочтительный URI для ресурса постоянный; `Location` указывает новый адрес. В этом случае сервер направил клиента с HTTP на HTTPS ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)).

Проверили переход по перенаправлению:

```bash
curl -sSIL --max-time 15 http://github.com | grep -Ei '^(HTTP/|location:)'
```

Вывод показал цепочку:

```text
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
HTTP/2 200
```

`-L` заставляет `curl` перейти по адресу из `Location`; `-I` по-прежнему запрашивает только заголовки. В первой попытке в фильтре `grep` пропустили `(`, из-за этого адрес `Location` не выводился; исправленный шаблон `^(HTTP/|location:)` показывает и статусы, и адрес перенаправления.

## Что важно запомнить

1. DNS связывает доменное имя с IP-адресом через DNS-резолвер.
2. `Non-authoritative answer` — обычная пометка ответа резолвера, а не ошибка.
3. VPN или локальная сеть могут направлять DNS-запросы через собственные резолверы; необычный адрес ответа сам по себе не доказывает точную конфигурацию.
4. `curl -I` позволяет проверить HTTP-ответ по заголовкам, не загружая тело страницы.
5. Код `200` указывает на успешный HTTP-ответ; IP-адреса сервиса могут изменяться.
6. HSTS сообщает браузеру использовать HTTPS; CSP и `X-Frame-Options` управляют загрузкой ресурсов и встраиванием страницы.
7. `301` — постоянное перенаправление, а `Location` указывает предпочтительный адрес назначения.
8. В `curl -L` ключ `-L` следует перенаправлению; последовательные статусные строки показывают каждый ответ по пути.
