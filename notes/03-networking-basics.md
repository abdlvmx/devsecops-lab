# Заметки под мой личный курс DevSecOps

## Тема 3. DNS и проверка HTTPS-соединения

**Статус:** начальная проверка DNS и HTTPS выполнена; далее изучаем HTTP-ответ.

### Цели

- Понять, как DNS связывает доменное имя с IP-адресом.
- Различать DNS-резолвер и авторитетный сервер.
- Проверять HTTPS-доступность и читать HTTP-статус.

## 1. DNS-запрос с VPN

Выполнена команда:

```bash
nslookup github.com
```

Наблюдение с включённым VPN:

```text
Server: 198.18.0.2
Address: 198.18.0.2#53

Non-authoritative answer:
Name: github.com
Address: 240.0.0.180
```

`Server` — DNS-сервер, которому отправлен запрос; `#53` означает порт DNS 53. Ответ `Non-authoritative` сам по себе не является ошибкой: ответ вернул резолвер, а не авторитетный сервер домена.

Диапазон `198.18.0.0/15` зарезервирован для тестирования сетевого оборудования, а `240.0.0.0/4` зарезервирован, а не предназначен для обычной публичной маршрутизации ([реестр специальных IPv4-адресов IANA](https://www.iana.org/assignments/iana-ipv4-special-registry)). По этому наблюдению можно предположить, что VPN использует DNS-посредник или синтетический ответ; конкретную конфигурацию VPN один запрос не раскрывает.

## 2. DNS-запрос без VPN

Повторный `nslookup github.com` без VPN показал:

```text
Server: 192.168.0.1
Address: 192.168.0.1#53

Non-authoritative answer:
Name: github.com
Address: 140.82.121.3
```

`192.168.0.1` — адрес из частного диапазона, часто используемый роутером или локальным DNS-посредником. `140.82.121.3` — публичный IPv4-адрес, полученный для имени в момент проверки. DNS-адреса могут меняться. GitHub публикует актуальные диапазоны своих IP через Meta API ([документация GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses)).

Разница между двумя ответами согласуется с тем, что VPN меняет путь DNS-запроса или способ отображения адресов. Это вывод по наблюдениям, а не установленная причина.

Проверили AAAA-запись с включённым VPN:

```bash
nslookup -type=AAAA github.com
```

Ответ VPN-резолвера `198.18.0.2` завершился `No answer`: в этом запросе не был возвращён IPv6-адрес. Это характеризует ответ данного резолвера в текущем VPN-режиме и само по себе не доказывает, что у домена вообще нет AAAA-записей.

## 3. Проверка HTTPS через VPN

Выполнена команда:

```bash
curl -I --max-time 15 https://github.com
```

Важные части ответа:

```text
HTTP/2 200
server: github.com
strict-transport-security: max-age=31536000; includeSubdomains; preload
```

- `-I` запрашивает только HTTP-заголовки, без тела страницы.
- `--max-time 15` ограничивает время выполнения 15 секундами.
- `HTTP/2 200` означает, что HTTPS-запрос завершился успешно и сервер вернул статус `200`.
- `server: github.com` обозначает сервер в HTTP-ответе.
- `strict-transport-security` — заголовок HSTS, сообщающий браузерам использовать HTTPS для домена.

В полном ответе `curl` присутствовали также cookie-заголовки; они не нужны для конспекта и здесь не сохраняются.

## 4. Заголовки безопасности

Чтобы не печатать длинные cookie-заголовки, статус и выбранные заголовки отфильтровали:

```bash
curl -sSI --max-time 15 https://github.com | grep -Ei '^(HTTP/|server:|strict-transport-security:|content-security-policy:|x-frame-options:|x-content-type-options:)'
```

Ответ содержал `HTTP/2 200`, HSTS, `x-frame-options: deny`, `x-content-type-options: nosniff` и длинную Content Security Policy.

- HSTS: `max-age=31536000` задаёт срок действия в секундах (примерно один год); `includeSubdomains` распространяет политику на поддомены ([RFC 6797](https://www.rfc-editor.org/rfc/rfc6797)).
- `X-Frame-Options: deny` запрещает браузеру показывать страницу во фрейме/iframe, что помогает против clickjacking ([RFC 7034](https://www.rfc-editor.org/rfc/rfc7034/)).
- `X-Content-Type-Options: nosniff` запрещает браузеру угадывать тип содержимого вместо использования заявленного MIME-типа ([Fetch Standard](https://fetch.spec.whatwg.org/)).
- CSP начинается с `default-src 'none'`, задавая запрет по умолчанию для ресурсов, для которых не заданы более конкретные правила. Дальше сервер перечисляет разрешённые источники для отдельных типов ресурсов. `frame-ancestors 'none'` запрещает встраивать страницу в другие страницы ([CSP Level 3](https://www.w3.org/TR/CSP/)).

## 5. Перенаправление HTTP на HTTPS

Проверили ответ на незашифрованный HTTP-запрос:

```bash
curl -sSI --max-time 15 http://github.com | grep -Ei '^(HTTP/|location:)'
```

Ответ:

```text
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
```

`301 Moved Permanently` сообщает, что предпочтительный URI для ресурса постоянный; `Location` указывает новый адрес. В этом случае сервер направил клиента с HTTP на HTTPS ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)).

Проверили переход по перенаправлению:

```bash
curl -sSIL --max-time 15 http://github.com | grep -Ei '^(HTTP/|location:)'
```

Вывод показал цепочку:

```text
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
HTTP/2 200
```

`-L` заставляет `curl` перейти по адресу из `Location`; `-I` по-прежнему запрашивает только заголовки. В первой попытке в фильтре `grep` пропустили `(`, из-за этого адрес `Location` не выводился; исправленный шаблон `^(HTTP/|location:)` показывает и статусы, и адрес перенаправления.

## 6. Проверка запроса в режиме IPv6

После того как `nslookup -type=AAAA github.com` с VPN не вернул AAAA-ответ, выполнили:

```bash
curl -6 -I --max-time 15 https://github.com
```

Ответ содержал `HTTP/2 200`: запрос успешно завершился в режиме IPv6, который запросил `curl -6`. Это не обязательно доказывает прямое IPv6-соединение именно до GitHub: VPN или прокси могут разрешать адрес и маршрутизировать запрос отдельно от системного DNS-резолвера, который проверял `nslookup`.

## 7. Проверка TCP-порта через `nc`

Проверили доступность HTTPS-порта GitHub:

```bash
nc -vz -G 5 github.com 443
```

Ответ: `Connection to github.com port 443 [tcp/https] succeeded!` Это подтверждает, что TCP-соединение к порту 443 установилось. `nc -z` не отправляет HTTP-запрос и не проверяет TLS; эти уровни проверялись отдельно через `curl`.

Сравнили порт HTTP:

```bash
nc -vz -G 5 github.com 80
```

Ответ: `Connection to github.com port 80 [tcp/http] succeeded!` Значит, TCP-соединения устанавливаются к обоим портам. Это не означает, что HTTP остаётся незашифрованным: предыдущая проверка `curl` показала перенаправление с порта 80 на HTTPS.

## 8. TLS-сертификат и проверка `curl`

Подробности HTTPS-соединения отфильтровали из verbose-вывода:

```bash
curl -sS -I -v --max-time 15 https://github.com 2>&1 | grep -Ei '^\*.*(SSL connection|Server certificate|subject:|issuer:|certificate verify)|^< HTTP/'
```

Важные строки:

```text
SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256
subject: CN=github.com
issuer: C=GB; O=Sectigo Limited; CN=Sectigo Public Server Authentication CA DV E36
SSL certificate verify ok.
HTTP/2 200
```

- `TLSv1.3` — согласованная версия протокола защиты соединения.
- `AEAD-CHACHA20-POLY1305-SHA256` — согласованный набор шифрования и проверки целостности.
- `subject: CN=github.com` — имя, указанное в сертификате.
- `issuer` — удостоверяющий центр, выдавший сертификат.
- `SSL certificate verify ok` означает, что проверка сертификата прошла. `curl` по умолчанию проверяет доверенную цепочку сертификатов и соответствие имени URL сертификату ([документация curl](https://curl.se/docs/sslcerts.html)).

`HTTP/2 200` подтверждает, что после установления TLS сервер также вернул успешный HTTP-ответ. Следующий шаг — посмотреть срок действия сертификата.

### Даты действия сертификата через `openssl`

Чтобы вывести сведения о сертификате, включая даты его действия, подключились к GitHub с указанием имени сервера для TLS (SNI):

```bash
openssl s_client -connect github.com:443 -servername github.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

Полученный вывод:

```text
subject=CN=github.com
issuer=C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
notBefore=Oct 30 00:00:00 2026 GMT
notAfter=Jan 27 23:59:59 2027 GMT
```

- `notBefore` — момент, начиная с которого сертификат действителен.
- `notAfter` — момент окончания срока действия. В этом наблюдении сертификат истекает 27 января 2027 года в 23:59:59 GMT.
- `GMT` — время по Гринвичу; дату окончания сертификата важно сравнивать с текущим временем.
- Сведения о сертификате могут измениться после его перевыпуска, поэтому эти даты относятся к проверке, выполненной 23 ноября 2026 года.

## 9. Метаданные HTTP-ответа через `curl -w`

Запросили только выбранные сведения о соединении и отбросили тело страницы:

```bash
curl -sS -o /dev/null -w 'HTTP status: %{http_code}\nHTTP version: %{http_version}\nRemote IP: %{remote_ip}\n' https://github.com
```

Результат при включённом VPN:

```text
HTTP status: 200
HTTP version: 2
Remote IP: 240.0.0.27
```

Повторили ту же команду без VPN:

```text
HTTP status: 200
HTTP version: 2
Remote IP: 140.82.121.3
```

В обоих случаях GitHub вернул HTTP 200 по HTTP/2, но адрес удалённого конца соединения различается. Это подтверждает, что наблюдаемое изменение связано с сетевым путём или разрешением адреса при использовании VPN; оно само по себе не указывает на проблему с HTTPS.

- `-o /dev/null` не сохраняет тело ответа.
- `-w` (write-out) печатает выбранные параметры после запроса: код HTTP, версию HTTP и IP удалённого конца последнего соединения `curl` ([документация curl](https://curl.se/docs/manpage.html)). Если используется прокси, удалённым концом соединения может быть прокси.
- `HTTP status: 200` — запрос завершился успешным HTTP-ответом.
- `HTTP version: 2` означает HTTP/2.
- `Remote IP` здесь — `240.0.0.27`. Ранее VPN DNS-запрос для `github.com` также вернул адрес из диапазона `240.0.0.0/4`; без VPN `nslookup` вернул `140.82.121.3`.
- IANA помечает диапазон `240.0.0.0/4` как зарезервированный ([реестр IANA](https://www.iana.org/assignments/iana-ipv4-special-registry)). Поэтому адрес `240.0.0.27` необычен для обычного публичного назначения. В сочетании с VPN DNS-ответом `240.0.0.180` это похоже на адресацию или преобразование, используемое сетевым слоем VPN, но сами результаты не позволяют точно определить механизм. При этом HTTPS-запрос завершился успешно, а ранее `curl` сообщил об успешной проверке сертификата.

## 10. Сравнение HTTP-методов `GET` и `HEAD`

Сделали `GET`-запрос, отбросив тело ответа, но измерив его размер:

```bash
curl -sS -o /dev/null -w 'GET status: %{http_code}\nBody bytes: %{size_download}\n' https://github.com
```

Результат: `GET status: 200`, `Body bytes: 537160`.

Затем выполнили `HEAD` через параметр `-I`:

```bash
curl -sS -I -o /dev/null -w 'HEAD status: %{http_code}\nBody bytes: %{size_download}\n' https://github.com
```

Результат: `HEAD status: 200`, `Body bytes: 0`.

`GET` обычно запрашивает представление ресурса вместе с телом. `HEAD` запрашивает заголовки без тела; он полезен, когда нужно проверить доступность ресурса и его метаданные, не загружая содержимое. Здесь оба метода получили статус 200, а тело было передано только для `GET`.

## Что важно запомнить

1. DNS связывает доменное имя с IP-адресом через DNS-резолвер.
2. `Non-authoritative answer` — обычная пометка ответа резолвера, а не ошибка.
3. VPN или локальная сеть могут направлять DNS-запросы через собственные резолверы; необычный адрес ответа сам по себе не доказывает точную конфигурацию.
4. `curl -I` позволяет проверить HTTP-ответ по заголовкам, не загружая тело страницы.
5. Код `200` указывает на успешный HTTP-ответ; IP-адреса сервиса могут изменяться.
6. HSTS сообщает браузеру использовать HTTPS; CSP и `X-Frame-Options` управляют загрузкой ресурсов и встраиванием страницы.
7. `301` — постоянное перенаправление, а `Location` указывает предпочтительный адрес назначения.
8. В `curl -L` ключ `-L` следует перенаправлению; последовательные статусные строки показывают каждый ответ по пути.
9. TLS защищает HTTPS-соединение; `curl` проверяет сертификат сервера и его соответствие имени сайта.
10. `notBefore` и `notAfter` в выводе `openssl x509 -dates` показывают начало и конец периода действия сертификата.
11. `curl -w` выводит выбранные метаданные ответа; `-o /dev/null` отбрасывает тело ответа.
12. `GET` запрашивает представление ресурса, а `HEAD` позволяет получить заголовки без тела ответа.
