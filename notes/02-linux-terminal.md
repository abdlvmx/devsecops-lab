## 5. Права доступа в `ls -l`

Для просмотра прав нескольких файлов выполнена команда:

```bash
ls -l README.md branch-practice.md notes/02-linux-terminal.md
```

Для каждого файла вывод начинается с `-rw-r--r--@`:

- первый `-` означает обычный файл;
- `rw-` — владелец может читать и изменять файл, но не запускать его как программу;
- первое `r--` — участники группы могут только читать;
- второе `r--` — остальные пользователи тоже могут только читать;
- `@` в macOS указывает на наличие расширенных атрибутов файла ([справка macOS по `ls`](https://man.freebsd.org/cgi/man.cgi?apropos=0&manpath=macOS+26.7&query=ls&sektion=1)).

Владелец всех трёх файлов — `abdlvmx`, группа — `staff`. Числа `269`, `96` и `5391` — размеры файлов в байтах. Никакие права в этой практике не менялись.

Для папки `notes` выполнена команда:

```bash
ls -ld notes
```

Вывод начался с `drwxr-xr-x@`:

- `d` означает каталог;
- `rwx` у владельца — читать список имён, создавать/удалять записи и проходить внутрь;
- `r-x` у группы и остальных — читать список и проходить внутрь, но не изменять содержимое;
- `@` указывает на расширенные атрибуты macOS.

У каталогов `x` означает право прохода/поиска по каталогу. Поэтому права на каталог не следует толковать точно так же, как права на обычный файл.

## 6. Учебный shell-скрипт без права запуска

Создан файл `permission-practice.sh`:

```sh
#!/bin/sh
echo "Hello from a practice script"
```

Команда `ls -l permission-practice.sh` показала:

```text
-rw-r--r--@ 1 abdlvmx staff 46 ... permission-practice.sh
```

У файла были права на чтение и запись для владельца, чтение для группы и остальных, но не было `x` (execute).

Затем выполнены:

```bash
chmod u+x permission-practice.sh
ls -l permission-practice.sh
./permission-practice.sh
```

После `chmod u+x` права стали `-rwxr--r--@`: у владельца появился `x`, права группы и остальных не поменялись. Запуск через `./permission-practice.sh` вывел `Hello from a practice script`.

В символической форме `u` означает владельца (user), `+` добавляет право, `x` — запуск. `./` запускает файл из текущего каталога.

Затем проверили числовую форму:

```bash
chmod 700 permission-practice.sh
ls -l permission-practice.sh
./permission-practice.sh
```

Права стали `-rwx------@`, и скрипт запустился.

В числовой форме права складываются из значений: чтение `4`, запись `2`, запуск/проход `1`. Каждая цифра задаёт права одной категории: владельцу, группе и остальным. Поэтому `700` означает `7` (`4+2+1`, `rwx`) для владельца, `0` (`---`) группе и `0` (`---`) остальным. Такой режим подходит, когда файл должен быть доступен только владельцу.

## 7. Как Git записывает исполняемые файлы

В индекс были добавлены учебный скрипт и новый конспект:

```bash
git add permission-practice.sh notes/02-linux-terminal.md
git status
git diff --cached --summary
```

Сводка показала:

```text
create mode 100644 notes/02-linux-terminal.md
create mode 100755 permission-practice.sh
```

`100644` — обычный файл, `100755` — исполняемый файл. Git сохраняет это различие по execute-биту; он не переносит в историю точные локальные права вроде `700` ([документация Git о режимах файлов](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). Поэтому скрипт с локальным режимом `700` записан в репозитории как исполняемый `100755`.

## 8. Поиск строк командой `grep`

В README искали слова:

```bash
grep -n "Git" README.md
grep -n "Linux" README.md
grep -i -n "linux" README.md
```

Результаты:

```text
7:- Git and GitHub
18:- Git basics: completed
8:- Linux and Bash
8:- Linux and Bash
```

`grep` оставляет строки, где найден указанный текст. `-n` добавляет номер строки. По умолчанию поиск различает регистр; `-i` ищет без различия заглавных и строчных букв. Поэтому `Linux` нашёлся и по запросу `linux`.

## 9. Конвейер команд (`|`)

Чтобы посчитать совпавшие строки, вывод `grep` передали команде `wc`:

```bash
grep -i "git" README.md | wc -l
grep -i "linux" README.md | wc -l
```

Команды вывели `2` и `1`. Символ `|` (pipe) передаёт стандартный вывод слева на стандартный ввод команды справа. Здесь `grep` находит строки, а `wc -l` считает их.

## 10. Код завершения команды

Проверили поиск заведомо отсутствующей строки и код последней команды:

```bash
grep -n "not-a-real-topic" README.md
echo $?
```

`grep` ничего не вывел, а `echo $?` напечатал `1`. Для `grep` это означает, что ни одна строка не подошла. Это не ошибка чтения файла: код `0` означает, что строки найдены, `1` — что совпадений нет, а код больше `1` указывает на ошибку (например, проблемы с файлом). Код `$?` нужно читать сразу после команды, потому что любая следующая команда заменит его своим статусом. [Справка GNU grep о кодах завершения](https://www.gnu.org/software/grep/manual/html_node/Exit-Status.html).

Положительный поиск:

```bash
grep -n "Linux" README.md
echo $?
```

Поиск вывел `8:- Linux and Bash`, а код завершения был `0`: совпадение есть.

Проверка ошибки чтения:

```bash
grep -n "Linux" file-that-does-not-exist.txt
echo $?
```

`grep` сообщил `No such file or directory`, а код завершения был `2`. В отличие от `1` (файл прочитан, но совпадений нет), значение больше `1` означает ошибку выполнения поиска.

## 11. Использование результата `grep` в условии

Проверили поиск без вывода совпавшей строки:

```bash
if grep -q "Linux" README.md; then
  echo "Linux topic found"
else
  echo "Linux topic not found"
fi
```

Получено `Linux topic found`: `grep -q` завершился с кодом `0`, и shell выполнил ветку `then`. Ключ `-q` подавляет найденную строку; остаётся только статус.

У простого `if` ветка `else` срабатывает при любом ненулевом коде. Поэтому он не различает «нет совпадения» (`1`) и ошибку чтения (например, `2`); это важно учитывать в более надёжных скриптах.

Проверили и ветку `else` на отсутствующем слове:

```bash
if grep -q "not-a-real-topic" README.md; then
  echo "Topic found"
else
  echo "Topic not found"
fi
```

Получено `Topic not found`. Так как `README.md` существует, это был код `1` (совпадений нет), а не ошибка чтения.

## 12. Раздельная обработка кодов `grep`

Чтобы различить совпадение, отсутствие совпадения и ошибку, код поиска сохранили в переменную:

```bash
grep -q "Linux" README.md
grep_status=$?

if [ "$grep_status" -eq 0 ]; then
  echo "MATCH"
elif [ "$grep_status" -eq 1 ]; then
  echo "NO_MATCH"
else
  echo "ERROR"
fi
```

Первая попытка завершилась сообщением `integer expression expected`: в проверке было написано `"grep_status"` без `$`, то есть shell получил слово, а не значение переменной. После замены на `"$grep_status"` тест выполнился и вывел `MATCH`.

`$` раскрывает значение переменной. В `[ "$grep_status" -eq 0 ]` команда `[` сравнивает числовое значение с `0`; `-eq` означает «равно».

Для отсутствующего слова тот же блок с `grep -q "not-a-real-topic" README.md` вывел `NO_MATCH`, подтвердив код `1`.

Для отсутствующего файла тот же блок с `grep -q "Linux" file-that-does-not-exist.txt` сначала показал сообщение `No such file or directory`, а затем вывел `ERROR`. Код `2` попал в ветку `else`, предназначенную для ошибок.

## 13. Скрипт `grep-check.sh` с аргументами

Создан скрипт `grep-check.sh`, принимающий искомое слово и путь к файлу. Он проверяет количество аргументов, запускает `grep -q`, сохраняет код в `grep_status`, сообщает `MATCH`, `NO_MATCH` или `ERROR` и возвращает соответствующий код завершения.

После `chmod u+x grep-check.sh` права файла стали `-rwxr--r--@`. Первый тест:

```bash
./grep-check.sh Linux README.md
echo $?
```

Вывел `MATCH`, затем код `0`. Проверка отсутствующего текста:

```bash
./grep-check.sh not-a-real-topic README.md
echo $?
```

Вывела `NO_MATCH`, затем код `1`. Проверка отсутствующего файла:

```bash
./grep-check.sh Linux file-that-does-not-exist.txt
echo $?
```

Показала диагностическое сообщение `No such file or directory`, затем `ERROR: grep failed with status 2` и код `2`.

Проверка запуска без аргументов:

```bash
./grep-check.sh
echo $?
```

Скрипт вывел `Usage: ./grep-check.sh PATTERN FILE` и код `2`, не выполняя поиск.

Проверили шаблон из нескольких слов:

```bash
./grep-check.sh "Git and GitHub" README.md
echo $?
```

Получены `MATCH` и код `0`. Кавычки передали `Git and GitHub` как один аргумент.

В скрипте `$#` — число переданных аргументов, `$1` — первый аргумент (шаблон поиска), `$2` — второй (путь к файлу). Кавычки в `"$pattern"` сохраняют значение переменной одним аргументом даже при наличии пробелов.

## 14. Перенаправление стандартного вывода (`>`)

Обычный вывод успешного запуска скрипта отправили из терминала во временный файл:

```bash
./grep-check.sh Linux README.md > /tmp/grep-check-output.txt
cat /tmp/grep-check-output.txt
```

В терминале команда `grep-check.sh` ничего не вывела; чтение файла через `cat` показало `MATCH`. Оператор `>` перенаправляет стандартный вывод в файл и перезаписывает его, если он уже существовал. Использован файл в `/tmp`, поэтому проект не изменился.

## 15. Перенаправление потока ошибок (`2>`)

Ошибку от `grep-check.sh` направили в отдельный временный файл:

```bash
./grep-check.sh Linux file-that-does-not-exist.txt 2> /tmp/grep-check-error.txt
echo $?
cat /tmp/grep-check-error.txt
```

В терминале первое сообщение не появилось. `echo $?` показал `2`, а `cat` вывел из файла:

```text
grep: file-that-does-not-exist.txt: No such file or directory
ERROR: grep failed with status 2
```

`2>` перенаправляет стандартный поток ошибок (stderr), не меняя код завершения команды. Обычный вывод называется stdout (поток 1), поток ошибок — stderr (поток 2).

## 16. Добавление в конец файла (`>>`)

Сравнили перезапись и добавление на временном файле:

```bash
echo "first line" > /tmp/redirect-demo.txt
echo "second line" >> /tmp/redirect-demo.txt
cat /tmp/redirect-demo.txt
```

Файл содержал две строки: `first line` и `second line`. `>` создал/перезаписал файл, а `>>` добавил строку в конец, сохранив прежнее содержимое.

## 17. Объединение stdout и stderr

Оба потока скрипта направили в один файл:

```bash
./grep-check.sh Linux file-that-does-not-exist.txt > /tmp/grep-check-all.txt 2>&1
echo $?
cat /tmp/grep-check-all.txt
```

Код остался `2`. В файле оказались и сообщение `grep` о ненайденном файле, и `ERROR: grep failed with status 2` от скрипта. В `> файл 2>&1` сначала stdout направляется в файл, затем stderr направляется в текущее назначение stdout.

## 18. Поиск файлов командой `find`

В проекте искали заметки Markdown и shell-скрипты:

```bash
find notes -type f -name "*.md"
find . -type f -name "*.sh"
```

Найдено:

```text
notes/01-git-basics.md
notes/02-linux-terminal.md

```

`find` начинает поиск из указанного каталога. `.` означает текущий каталог, `notes` — подпапку проекта. `-type f` оставляет обычные файлы, `-name` фильтрует имена по шаблону. Кавычки вокруг шаблона оставляют раскрытие `*.md` или `*.sh` самой команде `find`.

Поиск по всему проекту:

```bash
find . -type f -name "*.md"
```

Нашёл четыре файла:

```text
./README.md
./notes/01-git-basics.md
./notes/02-linux-terminal.md
./branch-practice.md
```

`./` в путях означает «относительно текущего каталога».

## 19. Поиск по нескольким файлам

Строку `Learning Progress` искали в README и во всех Markdown-файлах папки `notes`:

```bash
grep -n "Learning Progress" README.md notes/*.md
```

Shell раскрыл шаблон `notes/*.md` в имена двух файлов до запуска `grep`. Для поиска в нескольких файлах `grep` добавил к каждой строке имя файла и номер строки, например `README.md:16:...`. Совпадения нашлись в README и обоих конспектах.

Количество совпадающих строк по файлам:

```bash
grep -c "Learning Progress" README.md notes/*.md
```

Результат: `README.md:1`, `notes/01-git-basics.md:3`, `notes/02-linux-terminal.md:3`. Опция `-c` считает строки, содержащие совпадение; если строка содержит фразу несколько раз, она всё равно считается один раз.

Контекст после совпадения:

```bash
grep -A 2 -n "Learning Progress" README.md
```

Результат показал строки 16–18: совпавший заголовок `16:## Learning Progress` и две следующие строки `17-` и `18-- Git basics: completed`. `-A 2` (`after`) просит показать две строки после совпадения; двоеточие отмечает совпавшую строку, дефис — строку контекста.

## Что важно запомнить

1. `pwd` показывает текущую папку, `whoami` — текущую учётную запись.
2. `ls -la` показывает все элементы папки, включая имена, начинающиеся с точки.
3. `cat` читает весь файл, `head -n` — заданное число первых строк, `wc -l` считает строки.
4. `.gitignore` влияет на то, что Git отслеживает, но не скрывает и не удаляет файлы с диска.
5. `Darwin` — название системы macOS; Linux и macOS имеют много общих команд, но не полностью одинаковы.
6. В строке `-rw-r--r--` первый символ показывает тип объекта, а следующие три пары — права владельца, группы и остальных пользователей.
7. `chmod 700` даёт владельцу `rwx`, а группе и остальным — `---`.
8. Git различает обычный файл (`100644`) и исполняемый файл (`100755`), но не хранит все локальные биты доступа.
9. `grep -n` ищет текст и показывает номера совпавших строк; `-i` игнорирует регистр.
10. `|` передаёт вывод одной команды на вход следующей, позволяя соединять небольшие команды в конвейер.
11. Код завершения `grep` помогает скрипту отличить найденный результат (`0`), отсутствие совпадений (`1`) и ошибку (больше `1`).
12. `if команда; then ... else ... fi` выбирает ветку по коду команды; `else` охватывает любой ненулевой код.
13. `"$1"` и `"$2"` обращаются к позиционным аргументам; кавычки сохраняют фразы с пробелами целиком.
14. `>` перезаписывает файл, `>>` добавляет в конец, `2>` перенаправляет stderr, а `> файл 2>&1` отправляет оба потока в один файл.
15. `find каталог -type f -name "шаблон"` ищет обычные файлы по имени внутри каталога и его подпапок.
